# Эксплуатация

Для актуального способа запуска используйте `docker compose up -d --build`: `compose.yaml` уже поднимает `terminal` и `coinglass`. Node standalone запускается командами из [корневого README](../README.md). Старые инструкции с дополнительным `-f compose.coinglass.yaml` оставлены для совместимости и в обычном запуске не нужны.

## Самостоятельный runtime

Рекомендуемый старт для личной установки: `docker compose up -d --build`. Compose запускает приложение и отдельный CoinGlass worker. Worker сохраняет снимки в volume `coinglass-data`; не удаляйте его при обновлении. Конфиденциальные файлы для сайта монтируются из `coinglass-secrets/` только для чтения. Образы используют read-only root filesystem, tmpfs, ограниченные capabilities и restart policy.

Готовый `release/` работает обычным Node.js. Всё frontend содержимое в release/public, сервер — один ESM bundle без npm runtime-зависимостей. Системному времени сервера и браузера нужно быть корректным; UTC-ось не зависит от locale устройства.

## Health и журналы

```bash
curl -fsS http://127.0.0.1:3000/api/health
docker compose logs -f --tail=100 terminal
```

Health проверяет жизнеспособность приложения, а не доступность Binance. Последние состояния поставщиков отдельно в providers. Логи также пишутся JSON-строками в stdout; Docker ограничивает файлы 10 MB × 3. UI-журнал ограничен 100 записями памяти и сбрасывается при рестарте. На Cloudflare журнал и uptime относятся к worker isolate; это не глобальная телеметрия всех запросов.

## Сетевой доступ

Для auto-режима сервер должен выполнять HTTPS GET к data-api.binance.vision и при подключении ключа api.twelvedata.com. Без доступа графики останутся в DEMO. Клиент обращается только к тому же origin /api, поэтому API-ключей/CORS к бирже в браузере нет.

Standalone включает саморегистрацию и вход по имени пользователя и паролю. Данные учётных записей и профилей хранятся в SQLite (`/data/divmoney.sqlite` в Compose), файл находится в постоянном томе `divmoney-data`. После входа доступны общий профиль (его настройки могут менять все зарегистрированные пользователи) и личный профиль; можно создать дополнительные личные профили, скопировав текущие настройки. Общие настройки синхронизируются между вошедшими пользователями, а личные видны только владельцу. Список отслеживания китов остаётся общим для установки.

Для публичного сервера рекомендуется задать в `.env` точный origin, например `PUBLIC_ORIGIN=https://terminal.example.com`. Если он не задан, приложение сверяет Origin с Host текущего запроса. `SESSION_COOKIE_SECURE=true` оставляйте включённым за HTTPS reverse proxy. Для локального HTTP-тестирования установите `SESSION_COOKIE_SECURE=false` и не публикуйте такой режим в сеть. В Compose порт приложения привязан к localhost; наружу публикуйте только HTTPS reverse proxy. При саморегистрации применяются минимум 12 символов пароля и ограничение частоты запросов входа/регистрации. Секрет сессии хранится в HttpOnly/SameSite cookie, а в SQLite записан только его хеш.

Пример минимального Nginx location за уже настроенным HTTPS server:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 20s;
}
```

Собственные внешние proxy-заголовки приложением для авторизации не используются. Не размещайте `.env`, SQLite-файл или исходный каталог как static root; сервер обслуживает только release/public. Задайте корректный `Host` в proxy и не отключайте TLS.

## Обновление

Сохраните .env и браузерные настройки, замените source и пересоберите образ:

```bash
docker compose up -d --build
```

Для ручного Node запуска остановите предыдущий процесс через SIGTERM, замените release, запустите снова под systemd/вашим process manager. SIGTERM/SIGINT вызывают server.close; request timeout ограничивает длительность запросов. Для отката храните предыдущий image tag или release-directory.

## Hosted-сборка

Публикация использует Cloudflare-compatible Worker из `dist/server/index.js` и assets из dist/client. Конфигурация `.openai/hosting.json` содержит identity и выключенные D1/R2 bindings. Runtime-секреты задаются окружением размещения. Готовый standalone release не читает этот файл и не зависит от Site identity.

## Диагностика

| Симптом                          | Проверка/действие                                                |
| -------------------------------- | ---------------------------------------------------------------- |
| Все криптовалюты DEMO            | DATA_MODE, доступ data-api.binance.vision, WARN в журнале        |
| Акции DEMO                       | Наличие ключа Twelve Data, права на биржу/символ, лимиты тарифа  |
| API зелёный, provider недоступен | Это разные проверки: приложение работает, котировки fallback     |
| Пустой список                    | Сбросьте поиск, избранное и фильтры; проверьте /api/markets      |
| Индикатор добавлен, линий нет    | Проверьте видимость, параметры и доступность MTF-истории         |
| График слишком растянут          | Кнопка сброса масштаба или двойной клик по шкале                 |
| Настройки профиля не обновились  | Проверьте вход, `/data` volume, права SQLite и ошибки API профиля |
| Логи на hosted неполные          | Они scoped к текущему isolate; используйте серверные stdout logs |

## Практические лимиты

SQLite-профили и авторизация рассчитаны на один standalone экземпляр с постоянным диском. Ограничение частоты попыток входа хранится в памяти одного процесса; для нескольких реплик нужны общий rate limiter и централизованное хранилище сессий. Общий профиль использует стратегию последней записи при параллельном редактировании. Это не заменяет резервное копирование и мониторинг сервера.

Для резервной копии остановите приложение (`docker compose stop terminal`), скопируйте volume `divmoney-data`, затем запустите его снова. Не удаляйте этот volume при обновлении; `docker compose down -v` удалит профили и учётные записи.

## Ресурсы и нагрузка

Ориентиры ниже предназначены для **одного персонального экземпляра**. Это стартовые лимиты для планирования, а не гарантированный максимум: фактическая нагрузка зависит от числа открытых вкладок, свечей (300–4000), включённых VMC/DRZ/SMC, скорости источников и количества пользователей.

| Режим                                                                 | CPU       | RAM      | Диск                                                                          |
| --------------------------------------------------------------------- | --------- | -------- | ----------------------------------------------------------------------------- |
| Запуск готового `release/` или одного контейнера                      | от 1 vCPU | от 1 GiB | от 1 GiB свободного места под runtime/образ и логи                            |
| Сборка из исходников или `docker compose up --build` на той же машине | от 2 vCPU | от 4 GiB | от 5 GiB свободного места под npm-зависимости, слои Docker и результат сборки |

Node.js 22.13+ обязателен для запуска без Docker. Контейнер использует Node 22 и встроенный SQLite через `node:sqlite`; Compose монтирует профильную базу в постоянный volume `divmoney-data`. Не запускайте несколько реплик на одном файле базы. Compose не устанавливает `mem_limit`/CPU quota: при размещении в Kubernetes или на общей машине задайте ограничения по результатам замеров. Веб-сервер слушает 3000/tcp; наружу при публикации нужен HTTPS reverse proxy. Для рыночных данных нужен исходящий HTTPS/443 к `data-api.binance.vision`, для HYPE также к `fapi.binance.com`, при использовании акций/индексов/forex — к `api.twelvedata.com`. Режим `DATA_MODE=demo` работает без внешних поставщиков.

На главной `/api/markets` опрашивается раз в 30 секунд, `/api/health` и `/api/logs` — раз в 10 секунд. На странице пары история загружается один раз, затем `/api/candles/latest` запрашивает две свечи каждые 30 секунд при видимой вкладке. Новый таймфрейм, изменение глубины, ручное обновление или разрыв истории запускают полную загрузку; Binance требует до `ceil(count / 1000)` запросов klines на один таймфрейм. Активные VMC/SMC с дополнительными таймфреймами могут загружать полные ряды при каждом обновлении основной свечи. Для многих одновременных пользователей и большого числа MTF-индикаторов нагрузка на API поставщика и CPU браузера будет значительно выше. Общий кеш Node ограничен 64 записями; настройки активного профиля синхронизируются через SQLite, localStorage используется как источник для ручного импорта старых настроек браузера.

Измеряйте на вашей конфигурации после запуска: `docker stats --no-stream`, `docker image ls`, `du -sh release`, `du -sh node_modules` (последнее — только на машине сборки). При запуске без Docker используйте `ps -o pid,rss,%cpu,cmd -p <PID>`; RSS показан в KiB. Проверьте отдельно сценарии 1000 и 4000 свечей, с включёнными индикаторами и нужным числом вкладок. Файлы JSON-логов Docker ограничены `10m × 3`, то есть до 30 MB плюс служебные расходы; историю котировок сервис на диск не сохраняет.

Контрольная проверка 12.09.2026, Node 24, локальный standalone в DEMO, BTCUSDT/1h: ответ 4000 свечей — 590 091 байт, короткий ответ двух свечей — 436 байт (JSON без сжатия). Это иллюстрация размера ответов, а не нагрузочный тест или гарантии для live-провайдеров. RAM/CPU в этой среде не измерены; ориентиры выше требуют проверки на целевом сервере.
