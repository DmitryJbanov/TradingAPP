# CoinGlass: фоновый парсинг и индикатор

## Что добавлено

Скрипты из coinglass_btc90 (3).zip интегрированы в services/coinglass. Сохранены исходные алгоритмы сбора tooltip-данных, OCR, проверки полноты карты, отбора локальных максимумов по высоте и выраженности. Добавлены HTTP-сервис, очередь заданий, протокол прогресса, хранение последнего успешного снимка и отображение на графике. Учётные данные из архива не включены в код или патч.

Патч tradingapp-coinglass.patch применяется поверх tradingapp-drawings-backlog.patch, после предыдущих патчей preferences и symbol-search. Из корня проекта:

```bash
git apply --check tradingapp-coinglass.patch
git apply tradingapp-coinglass.patch
npm run typecheck
npm run test:core
npm run build:standalone
```

После сборки перезапустите сервер. Для работы парсера нужно также запустить Python-сервис одним из способов ниже. Запуск только Node-сервера не запускает Python автоматически.

## Docker Compose

Подготовьте каталог coinglass-secrets в корне проекта. Поместите туда **credentials.txt из предоставленного архива**, содержащий email= и password=. Этот каталог исключён из Git и контекста сборки терминала. Не добавляйте секреты в коммит.

Контейнер парсера работает с UID 10001. Файлы секретов должны быть доступны ему для чтения; на Linux после копирования можно выполнить:

```bash
sudo chown -R 10001:10001 coinglass-secrets
sudo chmod 700 coinglass-secrets
sudo chmod 600 coinglass-secrets/credentials.txt
```

При наличии действующего Playwright storage_state можно также поместить его в coinglass-secrets/session.json. Это должен быть полноценный JSON состояния Playwright, а не произвольная выгрузка cookies. Такой файл имеет приоритет над автоматически сохранённой сессией; удалите импортированный файл, когда он больше не нужен. Если файл есть, дайте ему те же права, что credentials.txt.

Запуск приложения вместе с парсером:

```bash
docker compose -f compose.yaml -f compose.coinglass.yaml up -d --build
```

Отдельный Dockerfile устанавливает Python, Playwright Chromium, Pillow и Tesseract. Браузер не требует графической среды или Xvfb. Порт парсера не публикуется на хост; Node обращается к нему внутри сети Compose. При желании задайте одинаковый COINGLASS_TOKEN через .env: Compose передаст его обоим сервисам. Никогда не передавайте этот токен в клиентский JavaScript.

Диагностика:

```bash
docker compose -f compose.yaml -f compose.coinglass.yaml logs --tail=100 coinglass
```

Результаты, сессия и диагностика находятся в именованном томе coinglass-data, внутри контейнера — /data. Обновление контейнера сохраняет том. Команда down -v удаляет этот том, включая сессию и результаты.

## Локальный запуск без Docker

Требуются Python 3.10+, Tesseract OCR с английским языковым пакетом и Chromium Playwright. Из корня проекта создайте окружение:

```bash
python -m venv services/coinglass/.venv
```

Windows PowerShell:

```powershell
services\coinglass\.venv\Scripts\python.exe -m pip install -r services/coinglass/requirements.txt
services\coinglass\.venv\Scripts\python.exe -m playwright install chromium
```

Создайте coinglass-data и поместите в него credentials.txt из архива. Tesseract должен находиться в PATH; иначе задайте переменную TESSERACT полным путём к tesseract.exe. Запустите сервис из корня проекта:

```powershell
services\coinglass\.venv\Scripts\python.exe services/coinglass/service.py
```

Linux:

```bash
services/coinglass/.venv/bin/python -m pip install -r services/coinglass/requirements.txt
services/coinglass/.venv/bin/python -m playwright install --with-deps chromium
```

Установите Tesseract средствами дистрибутива, создайте coinglass-data/credentials.txt и запустите:

```bash
services/coinglass/.venv/bin/python services/coinglass/service.py
```

Python-сервис по умолчанию слушает 127.0.0.1:8090. В .env терминала добавьте `COINGLASS_SERVICE_URL=http://127.0.0.1:8090` и в другом терминале выполните `npm run start:standalone`. Для фоновой эксплуатации используйте Compose или менеджер служб ОС.

Переменные Python-сервиса: COINGLASS_HOST, COINGLASS_PORT, COINGLASS_DATA_DIR, COINGLASS_CREDENTIALS, COINGLASS_SESSION_FILE, COINGLASS_TOKEN, TESSERACT. По умолчанию данные и credentials.txt находятся в ./coinglass-data относительно каталога запуска; рабочая сессия сохраняется как session.json. COINGLASS_SESSION_FILE задаёт дополнительный импортированный файл сессии. Веб-приложению нужны только COINGLASS_SERVICE_URL и, при настройке авторизации, COINGLASS_TOKEN.

Для Cloudflare/другого hosted-развёртывания Python-сервис также нужен отдельно на сервере/контейнере. В worker-isolate Python и Chromium не запускаются. Укажите в серверном окружении доступный URL этого сервиса; при доступе через публичную сеть используйте HTTPS и COINGLASS_TOKEN. Прямой доступ из браузера пользователя к сервису не требуется.

## Использование

1. Откройте поддерживаемую криптопару, затем «Индикаторы» → «CoinGlass · Уровни ликвидаций» → добавить.
2. В блоке под графиком откройте «Настройки CoinGlass». Можно задать минимальную высоту пика относительно максимума карты, выраженность пика, количество уровней, сторону относительно цены снимка и задержку наведения при сборе. Период карты фиксирован: 90 дней.
3. Сохраните настройки и нажмите «Запустить / обновить парсинг». Изменение настроек само по себе не запускает браузер и не пересчитывает старый снимок. Цвета линий, толщина и подписи обновляются после сохранения без нового парсинга.
4. Прогресс, состояние и ошибки доступны под графиком. На главной внутри Backend отображается состояние фонового сервиса и последние задания; сообщения скриптов включены в общий журнал INFO/WARN/ERROR. Состояние опрашивается каждые 5 секунд, общий журнал — каждые 10 секунд. Журнал содержит последние события текущего запуска сервиса.
5. После успешного завершения уровни автоматически появляются на графике. Повторная кнопка выполняет новый сбор и заменяет снимок только после успешной проверки. При ошибке старые уровни остаются с предупреждением. Дата снимка и предупреждение об устаревании отображаются явно.

Прогресс этапный: вход, загрузка карты, выбор 90 дней, сбор пикселей/уровней, проверка пропущенных интервалов, расчёт пиков, готово. Это показатель прохождения этапов, а не точный прогноз оставшегося времени.

CoinGlass отдаёт сводную карту **актива**, а не конкретного контракта Binance. Поддерживаются криптопары в USD/USDT/USDC; USD-уровни накладываются на их графики с явной подписью источника. Для кросс-пар вроде ETHBTC наложение отклоняется. Поддержка актива подтверждается точным выбором в интерфейсе CoinGlass; недоступные активы завершаются ошибкой. Совпадение названия тикера не гарантирует наличия карты. Spot/Futures одного базового актива используют общий снимок. Отбор сторон, ближайших пиков и цвет линий относятся к цене **снимка CoinGlass**, а не к текущей цене Binance.

Один индикатор CoinGlass на рабочую область; его настройки сохраняются общим механизмом индикаторов. Снимки хранятся на сервере отдельно по базовому активу. Новый успешный запуск для актива обновляет его общий снимок, доступный всем пользователям этого экземпляра сервиса. При несовпадении настроек текущего индикатора с настройками снимка показывается предупреждение.

## Без окон, ошибки входа и защита данных

Рабочий процесс всегда запускает Chromium с headless=True, PWDEBUG отключён. Нет перехода на оконный режим или Xvfb. В Windows дочерний Python и вызовы Tesseract запускаются с CREATE_NO_WINDOW. Не нужно запускать браузер вручную для штатного парсинга.

Если CoinGlass требует CAPTCHA/2FA или сессия истекла, сервис сообщает об ошибке входа и завершает задание; окна не открываются и защита сайта не обходится. Можно предоставить действующую сессию в указанном выше формате. Сбор зависит от доступности сайта, доступа аккаунта к 90-дневной карте и неизменности структуры страницы.

Начиная с `coinglass-auth-v3` сервис и CLI используют один и тот же полный Chromium с `channel='chromium', headless=True`. До этой версии worker запускал отдельный Chromium Headless Shell, в отличие от исходного CLI. Параметры браузера находятся в `services/coinglass/browser_runtime.py`.

Новый метод начинает с главной страницы `/ru` (при 404 — `/`), закрывает видимый запрос cookie кнопкой Decline и использует ссылку входа, предоставленную страницей. При отсутствии/неработоспособности ссылки проверяет `/ru/login`, затем `/login` только при 404. После явной проверки браузера, HTTP 401/403/429 вход останавливается. При наличии обоих видимых и доступных полей отправляет форму один раз. Перенаправление считается только кандидатом на рабочую сессию: доступ подтверждается загрузкой и проверкой карты за 90 дней в сборщике, как и раньше.

`runs/<job-id>/login-state.json` теперь обновляется по этапам, в том числе при успешном открытии формы. Он содержит `revision`, `saved_at`, `run_id`, `stage`, `outcome`, `credential_submission`, историю кодов ответов документов и счётчики ошибок загрузки JS/CSS/XHR. Адреса ограничены известными публичными путями; параметры URL, тексты страниц, значения полей, заголовки, cookies и скриншоты входа не сохраняются. Сообщения этапов передаются в мониторинг backend.

HTTP 404 означает, что конкретный запрос получил ответ «не найдено». Этот код не доказывает блокировку IP. `challenge_detected: false` означает только отсутствие распознанных видимых признаков проверки. `credential_submission: not_sent` означает, что кнопка отправки не нажималась; `attempted` — что был вызван клик, но не доказывает получение данных сервером. `form_ready` подтверждает доступность формы, а не успешный вход.

Применение переработки поверх двух предыдущих исправлений входа:

```powershell
git apply --check .\tradingapp-coinglass-auth-rework.patch
git apply .\tradingapp-coinglass-auth-rework.patch
docker compose -f compose.yaml -f compose.coinglass.yaml up -d --build --force-recreate coinglass
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --version
```

Ожидаемая версия — `coinglass-auth-v3`; эта же версия появляется в журнале backend при запуске сервиса и каждого задания. Если команда отсутствует или версия другая, запускается старый образ/другой проект Compose.

После завершения текущих заданий выполните проверку формы в самом контейнере:

```powershell
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --probe
```

Проверка запускает тот же метод и браузер, но в чистой сессии и без чтения/отправки credentials.txt. Окон не открывает. Ожидается `outcome: form_ready`, `credential_submission: not_sent`. Она не проверяет пароль и права аккаунта на карту. После её успеха запускайте парсинг из интерфейса.

Последняя диагностика выбирается по времени записи, а не по случайному UUID:

```powershell
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --latest
```

Прежнюю команду `find ... | sort | tail -n 1` не используйте: она могла показывать ошибку старого задания. Новый вывод указывает ID, время, версию и полный путь конкретного файла; диагностические запуски имеют ID `probe-...`. Для локального запуска команды аналогичны: `python services/coinglass/diagnose.py --version`, `--probe` или `--latest` из корня проекта, тем же Python, которым запущен сервис. После обновления кода локально перезапустите `service.py`.

Переработанный метод проверен сценарными тестами: маршрут через интерфейс при 404 прямых адресов, отказ 403, проверка браузера, отсутствие поля почты, отклонённый вход без повторной отправки, перенаправление сохранённой сессии, очистка секретов и выбор свежей диагностики. Публичная форма проверена в доступном браузере. Реальный запуск внутри пользовательского Docker-контейнера и вход с аккаунтом здесь не воспроизводились; `--probe` проверяет именно эту среду.

Пароли и cookies не передаются в веб-интерфейс и журналы. Сырые исключения Playwright не публикуются; статус содержит безопасное описание ошибки. Диагностические изображения карты и JSON находятся только в каталоге данных сервера и не раздаются HTTP-сервисом. Технические ошибки запуска проверяйте по установленным зависимостям и доступности каталога данных. Сервис не содержит торговых операций и не требует API-ключа Binance.

## Исправление запуска Chromium в read-only контейнере: v3.1

`TargetClosedError` до первого сообщения `bootstrap` относится к запуску браузера или созданию контекста/вкладки. Эта ошибка сама по себе не указывает на неверный пароль, CoinGlass, OCR или конкретную причину завершения процесса.

В образе `coinglass-auth-v3.1` заданы `XDG_CONFIG_HOME=/tmp/coinglass-config`, `CHROME_CONFIG_HOME=/tmp/coinglass-config` и `XDG_CACHE_HOME=/tmp/coinglass-cache`. Chromium использует доступный для записи tmpfs вместо домашнего каталога пользователя, который в данном Compose доступен только для чтения. Перед запуском проверяется фактическая возможность записи. Источник правил выбора каталогов: [документация Chromium](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/user_data_dir.md).

Теперь сбои на этапах `browser_directories`, `browser_launch`, `context_create`, `page_create` сохраняются в `runs/<id>/browser-start.json` и `login-state.json`; они отображаются в backend отдельно от ошибок входа. Поле `signals` содержит распознанные признаки из исключения: например `read_only_filesystem`, `permission_denied`, `crashpad`, `missing_browser`, `missing_library`, `resource_limit`, `sigtrap`, `sigsegv`, `sigkill`. Пустой список означает, что причина не определена. `sigkill` сам по себе не доказывает OOM. Сырой stderr, окружение и содержимое сессии в отчёт не попадают. `--probe` выводит свежую диагностику также при сбое запуска, когда запросов к CoinGlass ещё не было.

Примените `tradingapp-coinglass-browser-start.patch` поверх `tradingapp-coinglass-auth-rework.patch` и пересоберите контейнер:

```powershell
git apply --check .\tradingapp-coinglass-browser-start.patch
git apply .\tradingapp-coinglass-browser-start.patch
docker compose -f compose.yaml -f compose.coinglass.yaml up -d --build --force-recreate coinglass
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --probe
```

В выводе должна быть версия `coinglass-auth-v3.1`. Для чтения отчёта задания, запущенного из интерфейса: `docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --latest`. Реальный запуск Docker в среде подготовки патча недоступен; исправление проверено тестами каталогов, обработки ошибок запуска и общего сценария worker. Успешный `--probe` в вашей среде подтверждает загрузку формы, после него проверяется вход и сбор из интерфейса.

## Проверка формы после перехода: v3.2

Отчёт v3.1 с `stage=site_login_link`, `page_path=/login` и обоими видимыми полями
означает, что переход состоялся, но сценарий завершился исключением до подтверждения
готовности формы. `credential_submission=not_sent` означает, что данные не отправлялись.
Видимость полей сама по себе не доказывает их доступность или успешный вход.
`http_status=null` возможен при переходе внутри приложения без нового HTTP-документа.
По старому отчёту нельзя определить точное исключение: оно было скрыто.

В `coinglass-auth-v3.2` чтение DOM при смене контекста/удалении элемента повторяется
с интервалом 250 мс в течение максимум 3 секунд перед последней попыткой. Проверка
доступности каждого поля использует таймаут 500 мс, чтобы исчезнувшее поле не
задерживало её на общий таймаут страницы. Эти параметры относятся к
[проверке is_enabled в Playwright](https://playwright.dev/python/docs/api/class-locator#locator-is-enabled).
Заполнение и отправка формы не повторяются. Если клик ссылки входа завершился
таймаутом, сценарий проверяет форму на текущей странице, прежде чем использовать
резервный URL. Ошибка закрытия браузера или неоднозначного селектора сразу
останавливает сценарий.

В `login-state.json` добавлены `operation`, `last_error` (этап, операция, тип и безопасный
код исключения), `observation_retries`, `email_input_count` и `password_input_count`.
`last_error` может присутствовать и после успешного восстановления; результат запуска
определяет `outcome`. Коды: `navigation_changed_dom`, `timeout`, `target_closed`,
`ambiguous_locator`, `unexpected_error`. Исходный текст исключения и значения полей
не сохраняются. Сообщение о восстановлении и конкретная операция при ошибке передаются
через существующий журнал worker в мониторинг backend.

Патч применяется **поверх v3.1** из корня проекта:

```powershell
git apply --check .\tradingapp-coinglass-navigation-wait.patch
git apply .\tradingapp-coinglass-navigation-wait.patch
docker compose -f compose.yaml -f compose.coinglass.yaml up -d --build --force-recreate coinglass
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --probe
```

Ожидаемая версия — `coinglass-auth-v3.2`, успешный результат проверки формы —
`outcome=form_ready`. После него запускайте парсинг из интерфейса: `--probe` не
использует учётные данные и не проверяет доступ аккаунта к карте. Если ошибка
остаётся, новый вывод содержит конкретную операцию и классификацию исключения.

Проверено 61 Python-тест, включая смоделированные переходы `/ru` (404) → `/`
(200) → `/login`, временный сбой чтения DOM, таймаут проверки поля, ограничение
повторов и отсутствие повторной отправки формы. Реальный Docker, вход и сбор
CoinGlass в среде подготовки этого патча не проверялись.

## Переход после отправки формы: v3.3

В v3.2 проверка `redirected_after_login()` принимала только четыре пути и
определённый заголовок. Любая другая страница того же сайта, записанная как
`other_coinglass_page`, приводила к таймауту даже при закрытой форме. Это дефект
проверки перехода; сам по себе старый отчёт не доказывает ни успешный вход,
ни неверный пароль. Список безопасных адресов диагностики больше не ограничивает
адреса, допустимые для перехода к проверке карты после отправки формы.

После однократной отправки v3.3 проверяет другой путь на том же HTTPS-домене,
отсутствие обоих полей, видимый документ и стабильность пути в течение двух секунд.
Точный заголовок не требуется. Страницы входа, регистрации и восстановления пароля
не считаются подходящими. Обнаруженный запрос одноразового кода, заголовок
подтверждения email или известный путь подтверждения завершают вход отдельной
ошибкой. Это распознавание известных признаков, а не гарантия обнаружения всех
возможных изменений интерфейса сайта. Проверки Cloudflare и HTTP-ошибок сохранены.

Результат остаётся `session_candidate`: это разрешение перейти к проверке карты,
а не подтверждение доступа аккаунта. Сборщик по-прежнему проверяет выбранный актив,
период 90 дней и отрисовку графика до сохранения сессии. При ошибке карты успешный
результат не публикуется. Для сохранённой сессии без отправки формы действует
прежнее консервативное условие. `--probe` по-прежнему не отправляет данные.

Диагностика дополнена `page_kind`, `redirect_basis` и
`additional_verification_detected`. Ожидаемая причина перехода после отправки —
`post_submit_route_changed_form_absent`. Неизвестные адреса, их параметры и
идентификаторы аккаунта не раскрываются. Сообщение о переходе к карте передаётся
через существующий журнал в мониторинг backend.

Применение поверх **v3.2**, из корня проекта:

```powershell
git apply --check .\tradingapp-coinglass-post-login.patch
git apply .\tradingapp-coinglass-post-login.patch
docker compose -f compose.yaml -f compose.coinglass.yaml up -d --build --force-recreate coinglass
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --version
```

Ожидается `coinglass-auth-v3.3`. Затем запускайте парсинг из интерфейса. Файл
учётных данных и том `/data` менять или удалять не требуется. При ошибке задания:

```powershell
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --latest
```

Проверено 69 Python-тестов, включая переход на неизвестный путь без нового
HTTP-документа и без ожидаемого заголовка, 2FA/email, отказ/ошибку HTTP, смену
домена, сброс таймера при смене пути, отсутствие повторной отправки, передачу
сообщений worker и отказ от сохранения сессии при недоступной карте. Реальный
вход и сбор в Docker пользователя в среде подготовки патча не выполнялись.

## Диагностика сборщика: v3.4

`outcome=session_candidate` в `login-state.json` означает, что сценарий перешёл
к проверке карты. Это не отчёт об успешном сборе. Ошибки сборщика записываются
в `page-state.json` той же папки запуска. В v3.3 команда `--latest` читала только
отчёт входа, а worker скрывал подробности ошибки сборщика за общим `RuntimeError`.

В v3.4 `--latest` дополнительно выводит `collection_diagnostic` из того же запуска.
В новых отчётах сборщика сохраняются этап, тип и безопасный код исходного исключения,
HTTP-статус начального запроса карты, время и идентификатор запуска. Ошибка ожидания
карты больше не заменяет исходный тип исключения на `RuntimeError`. В мониторинг
backend передаётся безопасное сообщение с этапом и типом. Значения полей, параметры
URL, неизвестные приватные пути и исходные тексты исключений не передаются.

Этапы различают навигацию, ожидание заголовка/графика, выбор актива и периода,
отрисовку 90-дневной карты, сохранение сессии, OCR, сбор подсказок, проверку пропусков
и расчёт пиков. `http_status` описывает ответ документа при открытии карты,
а не результат всех последующих запросов данных.

Этот патч исправляет диагностику. Он не подтверждает причину недоступности карты
и не меняет её селекторы, настройки аккаунта или алгоритм сбора.

Применение поверх v3.3:

```powershell
git apply --check .\tradingapp-coinglass-collection-diagnostics.patch
git apply .\tradingapp-coinglass-collection-diagnostics.patch
docker compose -f compose.yaml -f compose.coinglass.yaml up -d --build --force-recreate coinglass
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --latest
```

Существующий `page-state.json` также будет включён в вывод без повторного сбора;
дополнительные поля появятся после следующего запуска. Не запускайте `--probe`
между заданием и `--latest`: probe создаёт собственный новый отчёт входа.
Проверено 72 Python-теста; реальный Docker и сбор CoinGlass здесь не запускались.

## Исправление 404 при открытии карты: v3.5

Снимок `404 Not Found — nginx` вместе с отсутствием заголовка и canvas означает,
что сборщик получил страницу ошибки при открытии `/ru/pro/futures/LiquidationMap`.
Ожидание графика и OCR не исправляют такой ответ. Это не подтверждение неверного
пароля. В v3.5 исправлен маршрут открытия карты и добавлена поддержка английских
подписей, необходимых при использовании адреса без `/ru`.

Сценарий сначала пробует видимую ссылку карты или меню Liquidation → Liquidation Map
на текущей странице. Если такой переход недоступен, открывает русский адрес,
а **только при 404** — `/pro/futures/LiquidationMap`. Если оба прямых адреса
вернули 404, предусмотрена одна попытка перехода через меню с главной `/`.
Запрос дополнительного подтверждения, Cloudflare, HTTP 401/403/429 и другие
HTTP-ошибки останавливают сценарий. При возврате формы входа доступ не признаётся.
Сессия остаётся в том же контексте браузера; повторной отправки пароля нет.

Заголовок сводной карты выбирается отдельно от карты Binance и Hyperliquid.
Поддержаны `Поиск`/`Search`, точный период `90 день`/`90 day`, английские
накопительные серии лонгов и шортов. Проверки актива, периода, перерисовки,
полноты данных и значимости пиков сохранены. Снимки содержат фактический
проверенный URL карты без параметров; пересчёт принимает оба известных URL.
Переходы и HTTP-статусы передаются в мониторинг backend и сохраняются
в `page-state.json.navigation`. Режим браузера остаётся без окон.

Публичные страницы: [русская карта](https://www.coinglass.com/ru/pro/futures/LiquidationMap),
[английская карта](https://www.coinglass.com/pro/futures/LiquidationMap).
В проверочном браузере подтверждены открытие английской карты напрямую и через
меню, наличие canvas, выбор ETH с заголовком `ETH Exchange Liquidation Map`,
пункт `90 day` и подпись `Cumulative Long Liquidation Leverage` в подсказке.
Это проверка публичного интерфейса: реальный вход и полный сбор за 90 дней
в Docker пользователя здесь не выполнялись.

Подготовлены два варианта одного исправления — применяйте **один**:

- `tradingapp-coinglass-map-route-from-v3.3.patch`: поверх v3.3, включает диагностику v3.4.
- `tradingapp-coinglass-map-route.patch`: поверх уже установленной v3.4.

Пример для v3.3 (для v3.4 замените имя патча в первых двух командах):

```powershell
git apply --check .\tradingapp-coinglass-map-route-from-v3.3.patch
git apply .\tradingapp-coinglass-map-route-from-v3.3.patch
docker compose -f compose.yaml -f compose.coinglass.yaml up -d --build --force-recreate coinglass
docker compose -f compose.yaml -f compose.coinglass.yaml exec coinglass python diagnose.py --version
```

Ожидается `coinglass-auth-v3.5`. Затем запустите парсинг BTCUSDT из интерфейса.
При ошибке `diagnose.py --latest` выводит отчёт входа и сборщика одного запуска.
Проверено 82 Python-теста, включая RU 404 → EN 200, переход через меню,
неработающие маршруты, остановку при ограничениях доступа и разбор английских подсказок.

## Очередь, хранение и ресурсы

Одновременно работает **один** браузер: это ограничивает нагрузку и исключает конкуренцию за файл сессии. Очередь — до 20 ожидающих заданий. Повторный запуск уже ожидающего/работающего актива возвращает 409. Время одного задания ограничено 20 минутами; при превышении завершается весь процесс и его дочерние процессы. После перезапуска сервиса незавершённые задания помечаются как прерванные, успешные снимки сохраняются. Автоматического расписания нет: запуск только по кнопке/API.

Сохраняются последний результат и состояние каждого актива в <ASSET>.json, рабочая сессия session.json и не более 20 последних папок диагностики runs/<job-id>. Ошибка очередного запуска не стирает предыдущий успешный результат. Журнал в памяти ограничен 100 событиями; Docker-ротация дополнительно ограничивает журналы контейнера.

Ориентир для планирования, не замер: резервируйте для парсера 2 vCPU и 2 ГБ RAM, для всего узла приложения с парсером — 4 ГБ RAM и около 5 ГБ свободного диска под образы, браузер и данные. Compose ограничивает парсер 2 CPU и 2 ГБ RAM, /tmp — 1 ГБ, /dev/shm — 512 МБ. Эти временные области также потребляют память; на тесном узле возможен OOM. Сбор обычно занимает несколько минут, зависит от скорости сайта, ширины карты и hoverMs; верхняя граница задания — 20 минут. Нагрузка на CPU и память возникает в основном во время работы браузера/OCR; между заданиями сервис ждёт запросы.

HTTP-интерфейс терминала: GET /api/coinglass/status, GET /api/coinglass/status?symbol=BTCUSDT, POST /api/coinglass/run с JSON symbol и params. Адрес и токен парсера задаются только на сервере. POST отклоняет запросы с чужим Origin и неверные параметры. Внутренний API Python: GET /status, GET /events, POST /jobs. Не публикуйте неавторизованный внутренний API в Интернет.

## Проверки

Выполнены TypeScript, 46 тестов приложения, 36 Python-тестов и standalone HTTP smoke-тест. Python-тесты включают исходный снимок из архива: проверка полноты и значимых пиков; новые тесты проверяют валидацию, повторные задания, восстановление после перезапуска, сообщения прогресса, успешное завершение, ошибки и таймаут дочернего процесса. Браузерная проверка использует управляемые ответы сервиса для проверки индикатора, настроек, повторного запуска, старого снимка при ошибке и мониторинга. Тестовые данные не используются как рабочие результаты приложения.

Реальная авторизация и сбор с сайта CoinGlass в этой среде не выполнялись; Docker-образ здесь не собирался. Первый реальный запуск выполните после размещения credentials.txt/сессии и установки зависимостей. Он проверит доступ аккаунта и актуальность селекторов сайта.
